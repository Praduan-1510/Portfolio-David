North Star

Section 1

Keel wins not by doing bookkeeping — QuickBooks does bookkeeping — but by being the first bookkeeper you can watch think. Every screen answers one of three trust questions.

  1. What did you do without me? → Activity (append-only, every entry has a reasoning trace)
  2. What do you need from me? → Approvals (context-rich decisions, never bare yes/no)
  3. What are you allowed to do? → Autonomy (visible rails, some permanently locked)
Plus one forward-looking view What's coming? → 90-day Forecast.

The prototype's job: make an owner feel they could trust this, within 60 seconds of looking at it.

Scope & Constraints

Section 2
  • Zero client-side JavaScript, in both builds. Interactivity comes from native elements: <a> navigation, <details> expandable reasoning traces, <input type="range"> sliders, form POSTs, :hover/:focus/:active states. This is a deliberate constraint — it proves the design system and information architecture before any framework decision, and the live server keeps it (its CSP sends default-src 'none' with no script-src at all).
  • Multi-page site sharing one stylesheet — mirrors the real IA and gives free deep-linking (FSD nav requirement) and predictable back-button behavior.
  • In app/, all data is hardcoded from the FSD's Tested examples, so the reference build shows the exact scenarios the spec validates. The server computes the same scenarios from its own ledger instead.

Two builds, one design system

Section 2b

There are two working builds of the same product. They are not copies of each other.

app/ is the frozen design reference: twelve pages, one hand-authored scenario, every figure typed in by hand. It records what the design system looks like when it is used well. server/ is the live product: it renders the same components from SQLite, so its figures move every time someone uses the app — an approval decided, a threshold changed, a day of activity added.

They share app/style.css. The server reads that exact file off disk and serves it at /style.css. There is no second stylesheet and no build step between them, so any change to the visual system is made once, in app/style.css, and both builds have it. The design system document describes that one file.

Because one build freezes a scenario and the other computes one, their numbers legitimately differ — the forecast curve, approval reference numbers, vendor counts, confidence scores, cash on hand. That is expected, and it is not to be reconciled. Do not edit the static pages to match the database, and do not reseed the database to match the static pages. When quoting a figure, say which build it came from.

Where the two differ in features, the server is the one that changes. If the static build shows something the server cannot do, that is a gap in the product, not permission to delete it from app/. The reference build loses a feature only when the product decides to drop it.

Recorded deviation from FSD §7

Deviation · 1 of 1 Recorded

FSD §7 requires that Activity and Approvals stay responsive at 10,000+ historical entries, and adds in parentheses "assumes virtualized list rendering, not pagination". This build does not virtualize. Activity pages through an indexed SQL LIMIT/OFFSET query, 25 events at a time, behind a rendered pager. Virtualized rendering needs client-side JavaScript, and the product ships none.

The requirement is the responsiveness. The parenthesis is an assumption about mechanism, written before the zero-JavaScript constraint, and the assumed mechanism is deliberately not used. The requirement itself is met: measured against a ledger of 10,043 events, Overview renders in about 4 ms, Activity 2 ms, Activity at page 400 7 ms, Approvals 2 ms, Forecast 3 ms, and the server test suite holds that line. This is the one place the build knowingly departs from a method the spec states.

Names that no longer match

Two static files keep their original filenames for historical reasons. app/settings.html is the Autonomy page (server route /autonomy), and app/cashflow.html is the Forecast page (server route /forecast). Titles, tab labels, and routes all say Autonomy and Forecast; only the filenames lag. Grepping app/ for either word will not find its file.

Screen-by-Screen Specification

Section 3

3.1 · Overview

index.html

Purpose: the 8 a.m. glance. "While you were away: Keel handled 23 items; 4 need your call."

  • Greeting line with date + trust summary sentence (plain language, FSD §3: no accounting jargon)
  • Stat strip (4 tiles): Cash on hand · Pending approvals · Autonomous actions this week · Est. time saved
  • Needs your call — top 2 approval items, condensed cards linking to Approvals
  • Recent entries — last 5 activity rows linking to Activity
  • Forecast strip — 13-week mini bar chart + the week-5 dip flag (FSD "Flagged a cash dip ahead")

3.2 · Approvals

approvals.html FSD §5.6

Every card: serial no. · proposed action · plain-language reasoning trace · confidence meter (ticks + number, FSD §7) · decision buttons. Both response shapes demonstrated.

3.3 · Activity

activity.html FSD §5.7
  • Append-only chronological ledger, newest first, grouped by day
  • Every entry expands (<details>) to full reasoning trace + attribution (KEEL · AUTO vs OWNER)
  • Includes: auto-categorizations (94%, 97%), recurring bill auto-payment under the $500 ceiling, first invoice reminder at 7+ days (§5.3), the cash-dip flag (a flag, not an approval — §5.5), an owner-resolved approval, and a correction entry that references its original rather than editing it — proving audit integrity visually.

3.4 · Forecast

cashflow.html FSD §5.5
  • Pure-CSS 13-week bar chart, y-axis + dotted gridlines, dashed red $10,000 floor line
  • Weeks 5–6 below floor → red bars + flag callout ("flag, never blocks an action")
  • Weeks 7–9 striped → visibly affected by pending approvals (Marlow & Vine receivable, Nordic Roasting payable), with a legend entry and an explanatory card listing them
  • Full data table below the chart (accessibility alternative + exact values)

3.5 · Autonomy

settings.html FSD §5.8 + §6
  • Adjustable rows: categorization threshold (90%, range 50–99) · bill ceiling ($500, up to $2,000) · cash-floor alert ($10,000, flag-only)
  • Fixed row: invoice reminders (auto at 7+ days; escalation always manual — not configurable)
  • Locked rows: New vendor payments · Disputes & anomalies — lock icon + "ALWAYS ASK" stamp + safety-rail framing ("This is a safety rail, not a limitation") per FSD onboarding intent

QA Checklist

Section 5 · Pre-delivery
  • Every autonomous action shown has a visible, human-readable reason (FSD goal: 100%, non-negotiable)
  • No approval item is a bare yes/no — all show action + reasoning + confidence + options
  • Confidence always ticks and number; debit/credit always sign and color
  • Locked categories cannot be mistaken for adjustable ones
  • Keyboard-only walkthrough of an approval decision works on every card
  • No horizontal page scroll at 375px; chart/tables scroll within their containers
  • Fonts load with display=swap; layout does not shift when they land

Beyond the Prototype

Section 6 · v1 product path

Written before server/ existed, and kept because most of it is still ahead of us. The server has since taken the first two steps its own way — no framework, an append-only event store, and the §6 rails enforced in src/engine/rules.ts — so read item 1's stack choice as one option that was not taken, not as a plan.

  1. Foundation — React/Next.js + the same design tokens; bank aggregator (Plaid-class, FSD §7: never store raw credentials); append-only event store for Activity (audit integrity is a data-model property, not a UI style).
  2. Agent loop — categorization with calibrated confidence (FSD §7: 90% stated ≈ 90% real; measure before tuning defaults), rules engine for §6 hard rails (rails enforced server-side, never only in UI).
  3. Trust instrumentation — track approval-vs-override rates per category to validate the FSD hypotheses (90% threshold, $10k flat floor, 5 hrs/week saved) with real data.
  4. Open questions still open (FSD §8): multi-account autonomy scope; what happens to in-flight approvals when a threshold changes; accountant read-only role. The fourth, list rendering at 10k+ entries (FSD §7), is settled — see the recorded deviation in §2b.

Every requirement ID above traces back to keel-fsd.md. If a screen and the FSD ever disagree, the FSD wins — then update this plan, not just the pixels. The single stated exception is the §7 rendering method, recorded in §2b.
