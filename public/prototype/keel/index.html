The project

Small business · bookkeeping · trust

The hard problem is not bookkeeping. It is how much of your money you let software touch.

Keel does the repetitive bookkeeping on its own, stops for anything high-stakes or ambiguous, and writes down why it did either. Every screen answers one of three questions: what did you do without me, what do you need from me, what are you allowed to do.

It was designed from a functional spec in which every requirement is marked Tested, Intent or Hypothesis, so the guesses are labelled as guesses rather than dressed up as findings. The visual system, “The Passbook”, borrows from the financial artifacts people already trust: the bank passbook, the ruled ledger, the typewritten statement, the rubber stamp. Paper is the most legible metaphor for a record that cannot be quietly rewritten.

Two builds came out of it. A twelve-page static design reference holding one hand-authored scenario, and a working server that renders the same components from SQLite. They share exactly one artifact, app/style.css, which the server reads off disk and serves verbatim. There is no second stylesheet and no build step between them.

Three things the code enforces

Not promises · constraints

No. 01

Append-only is a database property, not a promise.

The events table carries BEFORE UPDATE and BEFORE DELETE triggers that call RAISE(ABORT), so no code path, accidental or deliberate, can rewrite history. A correction is a new row pointing at the one it supersedes, and a test re-reads the superseded row to prove it is untouched.

server/src/store/eventStore.ts

No. 02

“No silent actions” is a NOT NULL constraint.

Every event requires a human-readable reason, written into the schema as reason TEXT NOT NULL CHECK (length(trim(reason)) > 0) rather than left to the code above it. An action with no stated reason cannot be recorded, so it cannot happen. The spec calls explainability non-negotiable; this is what non-negotiable looks like in a table definition.

server/src/store/eventStore.ts

No. 03

The locked rails are not settings.

First payment to a new vendor, and anything touching disputes or anomalies, always stop for a human. They are constants in the rules engine, checked before configuration is read. The tests set every dial to its most permissive legal value and assert the rails hold; an auto-pay ceiling POSTed past the UI still clamps to $2,000.

server/src/engine/rules.ts

A note on what this is

Nothing hidden
Prototype

A design and functional prototype, on mock data.

Nothing here touches a real bank account, and none of it is production-hardened. Both builds run on seeded books. Wiring a real aggregator needs a commercial account and a compliance review, so the bank adapter is a stub that throws with an explanation rather than a demo that pretends. Whether a stated 90% confidence really means 90% accuracy can only be settled by real outcomes over real time, so the spec states it as a hypothesis and the build leaves it unmeasured.

The static pages and the server also disagree about their numbers, on purpose. One freezes a hand-authored scenario so the design can be read cold. The other computes everything from live data and moves as you use it. That difference is documented, not reconciled.
